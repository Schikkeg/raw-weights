API Key Security

Sharing an API key with a web app is always a trust question — and a fair one. Here is exactly how ThreatScope handles it, and a workaround if you'd rather not share at all.

🔐 How the key is stored

✓

Browser session only — stored in st.session_state, which lives in server memory tied to your active session. It is never written to disk, never logged, never persisted.

✓

Clears on refresh — close the tab or refresh the page and the key is gone. No trace remains on the server.

✓

Sent directly to AbuseIPDB only — passed as an HTTP header (Key: <your_key>), never in a query string, never to any other endpoint.

✗

Not zero-risk — this is a public Streamlit app. If you have a high-value key or quota concerns, use the workaround below.

💡

The zero-key workaround

Don't believe in sharing keys with web apps — fine. Here's how to use ThreatScope without entering your key at all.

1

Use AbuseIPDB directly from your own machine

Run a curl or any HTTP client against the AbuseIPDB API with your key — on your own computer where you're comfortable.

2

Save the raw JSON response

Take the JSON dump — a /check or /blacklist response — and save it to a file. Your key never leaves your machine.

3

Upload to ThreatScope — no key needed

Go to IP Analysis → Load JSON Response and upload the file. ThreatScope renders the full visualisation — gauge, timeline, raw intel — without touching the API or asking for a key.

This is also the right approach for reviewing saved data offline, sharing findings with a colleague, or re-examining a response without burning daily quota.

How It Was Built

⚡

Running in edit mode — auto-accept on

Claude Code ran with auto-accept enabled throughout. Every file edit, every shell command, every dependency install applied without a per-step permission prompt. Here is what that actually means in practice:

👁️

Everything visible in real time

Every file being written, every command being run, scrolls in the terminal as it happens. You see it all.

🎯

Not passive — active monitoring

The skill is reading what's being built and knowing when to redirect. You're steering, not watching.

🚀

Full speed execution

No confirmation dialogs slowing the loop. Decision making stays with you; execution speed is near-instant.

🧟

Stop watching and things break

A zombie Streamlit process ran for 8 hours unnoticed. The moment you stop monitoring is when things go sideways.

Think of it like pair programming where your pair never gets tired or loses context — but you're still the one who knows where you're going and whether you've arrived.

Bonus attempt: automated video & audio with Playwright

Did not go well

Since the tool was built by vibe coding, I thought — why not automate the video recording and narration the same way? Asked Claude Code to write a Playwright script that would:

✓Open the live app in headless Chrome
✓Navigate through every tab automatically
✓Type IPs character by character (natural look)
✓Record the session as a WebM video
✓Generate TTS narration via edge-tts
✓Combine both with moviepy into an MP4

What actually happened

✗Streamlit's WebSocket state doesn't update reliably in headless mode — the Connect button never actually connected
✗After entering an IP and clicking Preview, the page didn't scroll to show the results — the video just showed a blank space below the button
✗Tab selectors in Streamlit's iframe structure needed multiple debugging rounds just to be found
~The audio worked. The video recorded. The scroll didn't happen. The combination was usable but not good enough to publish.

On the learning list

Playwright prompting for Streamlit apps — getting scroll timing, iframe targeting, and WebSocket state right — is a skill in itself. Will revisit. Manual recording for now.

In the Trenches

Seven real errors. Every one instructive. This is the part most write-ups skip.

1
ModuleNotFoundError No module named 'app'

Streamlit adds the script's directory to sys.path, not the project root. Fixed with a one-liner at the top of main.py inserting the root path.

2
AttributeError 'list' object has no attribute 'get'

Blacklist response has data as a 10,000-item list. The check parser expected a dict. Added detect_response_type() — now auto-routes both formats.

3
Deploy Fail Three missing things at once

No requirements.txt

Generated via uv export

Python 3.13

Cloud max is 3.12

Wrong remote

Code never pushed to origin

4
🧟 Zombie Process Changes not showing — incognito didn't help

A Streamlit process from 1:50 AM was still alive on port 8501. Every browser request hit the old code. Cache clearing and incognito are browser-side — the server-side zombie had to be killed explicitly.

5
StreamlitDuplicateElementId plotly_chart collision

Same gauge rendered twice in two sub-tabs — same score, same config, identical auto-generated IDs. Fixed by threading a key param through every chart call.

6
Git Remote Mismatch VS Code pushing to wrong repo

Two remotes: ThreatScope → correct ai.git; origin → empty ThreatScope.git. VS Code always pushes to origin. Fixed by updating origin's URL and removing the duplicate.

7
UnicodeDecodeError Production CSV upload crash

Excel adds a BOM that pandas can't handle with default UTF-8. Fixed by trying four encodings in sequence: utf-8-sig → utf-8 → latin-1 → cp1252.

Playing Every Role

This is what GenAcademy means by understand & orchestrate. Not writing every line — making every decision.

PM

Requirements

Translating "site going down" into API constraints, data requirements, quota limits, error handling policy, and zero-wasted-data as a design principle.

SA

Architecture

Module split, caching strategy, auth gate pattern, demo mode design, response type detection — all before any code was written.

QA

Testing

Found real bugs by actually using the thing. Uploaded a blacklist JSON to the check tab and watched it crash. Hit a Unicode error with an Excel CSV in production.

DO

DevOps

Streamlit Cloud needs requirements.txt, a supported Python version, and a valid remote. None were right first time. Learning what the platform needs is part of the work.

UX

User Experience

Help text, error messages, rate limit warnings, demo friction removal, feature cards. These are communication decisions — someone has to make them.

✍️

Documentation

README, video script, intro slide, this post. Documentation makes the project real. If nobody understands what you built or why, the build didn't fully happen.
