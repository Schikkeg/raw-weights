01

Product Thinking

The metric every speech product optimizes for is the wrong one

Industry standard metric

WER

Word Error Rate

% of transcribed words that differ from ground truth. Every leaderboard, every benchmark, every product announcement leads with this number.

The problem

A model can have excellent WER and still leave users editing every single output. Accuracy ≠ trust.

The better metric

ZER

Zero Edit Rate

% of dictations a user sends without editing. Measures whether they trusted the output enough to use it as-is.

Why it's right

It directly measures the thing that creates habit: trust. And trust is the only thing that makes a dictation tool sticky.

The takeaway you can apply today

Whatever product you're building — find the metric that measures user trust, not model capability. They are almost never the same metric.

02

Architecture

Never combine your transcription model with your formatting model

The instinct is to build one model that does everything — takes audio in, produces clean formatted text out. That instinct is wrong. Keeping them separate is one of the most consequential architectural decisions in the stack.

Two separate models, two separate jobs

ASR Model → "um let's meet at 5 o'clock oh actually let's meet at 3 o'clock"
raw, unfiltered, high-speed, optimized for accuracy only
Format Model → "Let's meet at 3 o'clock."
backtracking · filler removal · style · email/slack format · emoji
🔄

Iterate independently

Improve formatting without touching the transcription model and vice versa. No coupling, no regression risk across the boundary.

🎯

Train on the right signal

ASR trains on audio-to-text accuracy. Formatter trains on edit pairs. Conflating these produces a model that's mediocre at both.

⚡

Run in parallel

Intermediate ASR passes can start while the user is still speaking. The formatter runs on the final transcript. Sequential only where it must be.

03

System Design

Context collection happens before a word is spoken — and it changes everything downstream

The same spoken sentence produces completely different ideal output depending on where the cursor is. A voice product that doesn't know its context is transcribing in the dark.

You say

"Hey, it was great to meet you. Let's connect soon."

In Gmail

Hi [Name],

It was great to meet you. Let's connect soon.

Best,
[Signature]

In Slack

hey, great to meet you! let's connect soon

Same words. Different app. Completely different correct output. Without context, there's no right answer.

Context also solves the homophone problem

When dictating into an email thread, the app knows which names are already in the conversation. "Brian" vs "Bryan" vs "Brayan" — the correct spelling is already on screen. The system traverses the surrounding text to surface those proper nouns and passes them to the ASR model before transcription. The raw transcript comes out correct, not just close.

04

Engineering Reality

The AI context layer everyone is building on top of was designed for blind people in 2001

♿

The Accessibility API is 23 years old and has not been modernized

Every modern AI desktop app that reads surrounding context — what app you're in, what text is on screen, what element is focused — is using the OS accessibility layer. It was built for screen readers. It is the de facto standard because there's nothing else.

Hundreds of ms

Response latency — per request

App crashes

Too many requests → receiving app can crash

OS throttling

Battery + perf impact leads to API rate limits

How to work with it properly

✓Event-driven, not polling — trigger lookups on app switch and dictation start, not continuously
✓Cache node paths — once you know where an important node lives in the tree, cache the path not the value
✓Always async — never block the UI thread waiting on an accessibility response
⚠Short dictations will miss context — there simply wasn't enough time to finish the lookup before the user was done

The underrated CS skill this requires: tree traversal under performance constraints — breadth-first vs depth-first over a live, mutating accessibility tree. This is classic algorithms coursework applied to a genuinely hard production problem.

The principle

For any product where the output appears on screen — AI, search, autocomplete — latency isn't a quality of life concern. It's the product. Users don't consciously notice 300ms. But they feel it, form habits around it, and churn because of it.

06

Counter-Intuitive UX

The UX decisions that seem wrong — and why they're exactly right

Two design choices that go against instinct, both driven by the same principle: keep people in the application they were already in.

Decision

Do NOT stream text back while the user is speaking

Why streaming seems right

→ Users can see progress and trust the system is working

→ Feels more responsive and alive

→ Every other dictation tool does it

Why it's actually wrong

→ You lose your train of thought watching words appear mid-sentence

→ Backtracking breaks — text is already inserted before you correct it

→ Forces the product into a text editor mindset, which breaks the "stay in your app" principle

Decision

Do NOT pull users into a dedicated document editing UI

The obvious alternative

→ Every competing dictation tool at launch made you dictate into their UI

→ Easier to build (you control the surface)

→ Easier to add editing features (formatting bar, playback, etc.)

Why the harder path wins

→ The whole value proposition is staying in flow — switching to another window destroys that

→ Users don't want to manage two places where their text lives

→ This interaction model has since been copied across the industry. First mover advantage in UX paradigm.

07

PMF Signal

The 20→80 shift is what product-market fit actually looks like

Day 1 user

20%

of typed words are dictated

5 months

Same user

80%

of typed words are dictated

A habit that took decades to form — keyboard typing — replaced by voice for 4 in every 5 words. That's not product engagement. That's behaviour change at the deepest level.

What makes this remarkable

Typing has been the dominant human-computer interface for over 40 years. People learned it in school, reinforced it daily for their entire adult lives. Replacing 80% of that input modality in 5 months is a behavioural change that most consumer apps never come close to.

The caveat to keep in mind

Users come back from vacation and reach for their keyboard first. The habit regresses. Retention is partly a growth and lifecycle problem — behavioral nudges, re-engagement email, habit reminders. PMF doesn't mean the product works itself.

08

Strategy

Build vs Buy comes down to one question — and it's not cost

The question that decides everything

Does this component have a data flywheel?

If usage generates training data that makes the model better — and if better performance drives more usage — you own it. If not, you pay for an API indefinitely, and that's the right call.

Own it when

→Your usage data is a training asset (edit pairs, corrections, context)
→You need behavioral control a third party won't prioritize (emoji, backtracking, formatting)
→Vendor failure means your product fails (core inference path)
→Latency or reliability requirements exceed what off-the-shelf provides

Pay the API forever when

→It's a generic capability — any LLM can do it, you have no differentiation
→You're still prototyping — prove PMF first, optimize cost second
→Unit economics aren't broken — "maybe in 5 years" is not a reason to build in-house today
→There's no training signal — your data doesn't make the model better for your use case

Prototype with APIs. Build conviction. Then own it.

Serving your own models correctly takes months and real money even for off-the-shelf open source. Do not start that project until a feature has proven PMF. And sometimes the answer stays "no" for years. Both are valid outcomes.

09

AI Agent Reality

AI coding agents are trained to be polite — and that's a serious engineering problem

Models have been trained not to tell you your code is bad. They are trained to be agreeable and helpful. In a code review context, this creates predictable failure modes that compound over time if you don't know to watch for them.

🦾

Anti-pattern perpetuation

Agents follow the patterns already in the codebase. Existing tech debt gets copied and propagated. They see the pattern, they match it. They will not question whether the pattern should exist.

🔧

Patching over problems

Given a broken thing, agents will add a conditional, add a try/catch, add a fallback. They won't say "this should be redesigned." Restructuring and questioning architecture requires explicit prompting.

🛑

Stops at plausibly correct

The agent stops when the code looks like it should work. Not when it's verified to work. There is a meaningful gap between those two states in production systems.

📋

Won't refactor unless pushed

Agents are unlikely to restructure, rename, or question the existing architecture. They'll work within whatever they find. You have to explicitly ask for a refactor — it won't volunteer one.

The counter-move

Use a second model to review the first model's work — adversarially. One model generates the plan or code. A different model tries to break it. Models catch different things, and an adversarial reviewer is not trying to be polite. This is multi-model review as a discipline, not a one-off trick.

10

Engineering Process

Move human judgment upstream — not out of the loop

Coding agents are now very good at mechanical correctness. That's the part that used to require careful human attention. The implication is not "humans are no longer needed" — it's that human judgment becomes most valuable earlier in the process.

Old model: human reviews code

1. Write a spec (rough)

2. Agent writes code

3. Human reviews implementation details

4. Catch logic errors in the diff

New model: human reviews the plan

1. Agent interviews you about assumptions

2. Sub-agents analyze blast radius, security, contracts

3. Human reviews the plan

4. Second model reviews the plan adversarially

5. Agent implements. Plan is the PR rubric.

🎯

Interview first

Force the model to surface all assumptions and ambiguities before it starts planning — not mid-implementation

🔍

Define done upfront

The plan must specify verification criteria before any code is written. If you don't define the finish line, the agent won't cross it

📋

Plan as PR contract

Review PRs against the agreed plan — not in a vacuum. The plan already had human eyes on it. The implementation just has to conform

Where human judgment is irreplaceable

Design, taste, architecture, naming, whether the feature should exist at all. These are not things models do well. They are exactly the things that separate a product people love from one that technically works.

11

The Compounding Habit

Using your voice to prompt AI agents makes them dramatically more effective

🎙️

"Agents don't care about precision communication. But they don't know what they don't know. Voice naturally makes you give more context — and that changes the quality of the output."

When you type a prompt you compress. When you speak you elaborate. The agent needs the elaboration.

A typed prompt

"Add error handling to the API client"

12 words. No context about what kinds of errors matter, what the retry policy should be, what the user sees, what's already handled elsewhere.

The same prompt spoken

"Add error handling to the API client — we need to handle 429s with exponential backoff because the AbuseIPDB free tier has strict limits, network errors should silently retry twice then surface a user-visible message, and 401s should clear the session and redirect to the key entry screen"

Speaking naturally adds context you'd have trimmed when typing. The agent now has everything it needs.

The meta-insight

Voice AI and coding AI form a feedback loop. Voice makes you better at prompting agents. Better prompts make agents more effective. More effective agents produce more things worth using voice for. This is the compounding habit that transforms how you work — and it starts with one dictated prompt.

The through-line across all 11

→The right metric is the one that measures trust, not capability
→Infrastructure changes move the product needle as much as features do
→Separation of concerns in ML systems is as important as in software
→The unglamorous details are the moat — vibe coding the surface is not the same as owning it
→A flywheel is not marketing language — it is the actual reason to build in-house
→Human judgment moves upstream, not out of the loop
