The 7 design levers

A RAG pipeline has exactly seven parameters you make conscious decisions about. Get the defaults right and you have a working system. Tune them with evidence and you have a production one. Ignore them and you get confident-sounding nonsense.

①

Chunk Size Default: 512 tokens

How many tokens each stored passage contains — smaller chunks give sharper matches, larger chunks give richer context per fetch.

512 tokens ≈ two solid paragraphs from a policy document.

②

Chunk Overlap Default: 10–15%

Tokens shared between adjacent chunks so meaning doesn't vanish at a hard boundary cut.

64-token overlap on a 512-token chunk: the closing sentence of chunk N opens chunk N+1.

③

Embedding Model Must match ingestion ↔ query

The neural network that converts text to a dense vector — every vector in your database must live in the same coordinate space.

Switching models mid-project means re-indexing everything. Lock it before you ingest a single document.

④

Top-K Default: 5

How many chunks are fetched from the vector database and placed into the LLM's context window on each query.

K=5 narrows 100,000 stored chunks down to 5 paragraphs the model actually reads.

⑤

Retrieval Strategy Dense / Sparse / Hybrid

Whether you search by meaning (embedding similarity), by keyword overlap (BM25), or both fused together.

"Refund policy" → dense finds semantic matches; BM25 catches exact phrase hits. Hybrid captures both.

⑥

Re-ranker Strongly recommended

A second-pass model that re-scores retrieved chunks by contextual relevance before the LLM sees them — eliminating near-miss noise.

Vector search finds the neighbourhood. Re-ranker finds the right house on the right street.

⑦

System Prompt Constraint Non-negotiable

The instruction that tells the LLM to answer only from retrieved context and say "I don't know" when the answer isn't there.

Without this, the model will fill gaps with training knowledge — plausibly, confidently, wrongly.

Embedding Model Picker

The embedding model converts text into a vector. Everything depends on choosing one and sticking with it. The same model must be used for ingestion and for querying. Different models produce incompatible vector spaces — mixing them makes cosine similarity meaningless.

→ Lower K, add re-ranker

"I don't know" too often

The right chunk isn't making it into the context window at all.

→ Raise K, fix chunking

Slow & expensive

High K means large context — most tokens aren't helping the answer.

→ Re-rank, reduce K

Retrieval Strategy Selector

How you search your vector database matters as much as what you store in it. Pick between semantic search (dense), keyword matching (sparse), or both combined (hybrid) — then decide whether a re-ranker is worth the overhead.

🧲

Dense

Converts query to a vector and finds closest stored vectors by cosine similarity — matches by meaning, not by words.

✓ "refund" matches "money back guarantee"

✓ Works across paraphrased queries

✗ Misses exact-phrase critical matches

✗ Embedding latency per query

Best for: conversational, multilingual, semantic search

🔑

Sparse (BM25)

Scores chunks by keyword frequency (TF-IDF / BM25). Fast, no neural inference, deterministic.

✓ Exact SKU, model number, legal citation hits

✓ No GPU required

✗ Synonyms are invisible to it

✗ Paraphrased queries return nothing

Best for: product codes, structured IDs, exact references

⚡

Hybrid

Recommended

Runs dense + sparse in parallel, fuses the two ranked lists using Reciprocal Rank Fusion (RRF).

✓ Captures meaning AND keywords

✓ Robust across diverse query types

✗ More infrastructure to maintain

✗ Slightly higher latency

Best for: production systems, mixed or unknown query patterns

Re-ranker

A second-pass model that re-scores retrieved chunks by contextual relevance — narrows noise before the LLM sees anything.

Bi-encoder

Independently embeds each chunk and compares to the query. Faster but less precise — good for large candidate sets.

e.g. BAAI/bge-reranker-base

Cross-encoder

Processes query + chunk jointly — reads them together rather than independently. Highest precision, slightly more latency.

e.g. Cohere Rerank, ms-marco-MiniLM

The practical mental model

Vector search casts a wide net. The re-ranker is a second person reviewing the catch and throwing back what doesn't belong before it reaches the kitchen.

Debug Signals — 12 Failure Patterns

The RAGAS evaluation framework and LlamaIndex's evaluation guide both make the same point: RAG failures decompose cleanly into retrieval-side and generation-side failures, and confusing the two wastes days of tuning in the wrong place. The two-metric approach below is how you locate the bug before you start fixing it.

The two-metric localisation protocol (from RAGAS / LlamaIndex eval docs)

Measure Context Recall first

Inspect the raw retrieved chunks for a failing query. Is the ground-truth answer present anywhere in the Top-K list?

Present → retrieval is working, dig into generation

Absent → chunking, K, embedding, or strategy issue

Metric: Context Recall (RAGAS), Retrieval Hit Rate (LlamaIndex)

Then measure Faithfulness

With the correct chunks confirmed present, does the LLM produce a grounded answer — or does it stray outside the provided context?

Grounded → check pipeline assembly (context passed correctly?)

Strays → system prompt constraint too weak

Metric: Faithfulness (RAGAS), Hallucination score
