Why agent evals are different

When an agent fails, the root cause is always one of three things. Each requires a different fix — and a different eval.

🎯
Outcome Failure
The final answer was wrong. The SQL didn't run. The task wasn't completed. Fix: better outcome eval.
🔀
Trajectory Failure
Right answer, wrong path. 12 tool calls when 2 would have done. 10× the cost. Fix: trajectory eval.
⚠️
Behavior Failure
It ignored the rule you explicitly gave it. Got the right answer the wrong way. Fix: behavior eval.

The Three Pillars

From Sinan Ozdemir's book and SDS podcast ep. 959. Anthropic calls these "grader types." Oracle adds state changes and recovery path. All roads converge here.

Did it get the right answer?

Outcome is the final artifact the agent produces — a SQL query, a written response, a completed action. It's the natural place to start because it answers the simplest question: did it work? But outcome alone tells you nothing about why it failed or how close it came to failing every other time.

Common trap: An agent that produces the right answer after 12 unnecessary tool calls still has a serious problem — one that outcome-only evals will never surface.

How to measure:

LLM-as-judge rubric Unit test / verifiable reward Pairwise comparison Gold set agreement rate pass@k / pass^k
Key insight (Anthropic): Calibrate your LLM judge against a gold set before trusting it. Have two domain experts independently evaluate the same task — if they disagree, the task spec is ambiguous, not the agent. Fix the task.
Was the path reasonable?

Trajectory is the sequence of decisions the agent made on the way to the outcome — which tools it called, in what order, how many times. Two agents can reach the same correct answer with very different trajectories. One may be 10× cheaper and 3× faster.

Real example: An agent writing SQL could look up evidence first (cheap vector search) then run one query — or run SQL blind, get an error, infer the schema from the traceback, and try again. Same number of tool calls. Very different cost profile. Outcome eval sees both as identical.

How to measure:

Tool call count Tool selection accuracy Step ordering Trajectory rubric (RULER / OpenPipe) Latency per tool call Token cost per trace
Key insight (Anthropic): Grade outputs, not specific paths. Penalizing a valid alternative route is the most common trajectory rubric mistake. Ask whether the path was efficient — not whether it matched your expected sequence.
Did it follow the rules?

Behavior is distinct from trajectory. Trajectory measures efficiency. Behavior measures compliance: did the agent respect the guardrails and constraints you explicitly gave it? This pillar is optional if you gave the agent no rules — but the moment you set a guardrail, you have something to measure.

Real example: GPT-4.1, even when explicitly told "always look up policy information before answering," still skipped that step 5% of the time. That's a behavioral failure — not a trajectory inefficiency, not an outcome error. Different root cause, different fix.
Rule adherence rate Guardrail trigger accuracy Out-of-scope refusal rate Human compliance review
Key insight (Oracle): Recovery path is a behavioral metric. When something goes wrong — wrong database, bad input, tool timeout — does the agent recover gracefully or fail silently? Explicitly inject failures and evaluate the recovery, not just the happy path.

Choosing Your Grader

Every eval needs something to score the agent. Click any card to expand.

⚙️
Code-Based
Deterministic · Fast · Brittle
Fast and cheap to run
Fully reproducible results
Can't handle valid variations
Requires deterministic output

Best for: Coding agents (unit tests), SQL correctness (does it run? right rows?), tool call verification, binary outcome checks, DOM/screenshot verification for computer use agents.

Methods: String matching, unit tests, static analysis, schema checks, file system state verification, database content checks.

Watch out for: Eval bypass — agents can sometimes find unintended loopholes that pass your code grader without solving the actual problem. Design defensively; review passing traces regularly.

🤖
LLM-as-Judge
Flexible · Scalable · Needs calibration
Handles open-ended outputs
Captures nuance and style
Non-deterministic by nature
Requires calibration against humans

Best for: Conversational agents (tone, brand voice), research agents (groundedness, coverage), trajectory evaluation (was this path reasonable?), behavior evaluation (did it follow the rules?).

Methods: Rubric-based scoring, natural language assertions, pairwise comparison, multi-judge consensus. OpenPipe's RULER prompt is a solid starting point for trajectory rubrics.

Watch out for: You're not looking for the smartest judge — you're looking for the one that agrees with you. Test against a gold set. Adding chain-of-thought reasoning and few-shot examples to the judge prompt can move agreement from ~70% to 100%.

👤
Human Grader
Gold standard · Expensive · Hard to scale
Matches real expert judgment
Calibrates your LLM judges
Slow and costly at scale
Hard to keep consistent

Best for: Calibrating LLM judges, mission-critical domains (legal, medical, financial), subjective quality where no rubric suffices, production spot-check sampling.

Methods: SME review, inter-annotator agreement testing, A/B preference testing, crowdsourcing for simpler tasks.

Watch out for: Two domain experts should independently reach the same verdict on any eval task. If they can't agree, fix the task spec — the ambiguity is in the task, not in the agent or grader.

The Consistency Problem

An 80%-accurate agent is not 80% reliable in production. Here's the math.

Per-trial success rate 80%
Number of calls (k) 5
pass@k
Succeeds at least once in k tries — good for "any working solution"
—
chance of ≥1 success
pass^k
Succeeds every single time — required for customer-facing reliability
—
chance of all k succeeding
Adjust the sliders to see your agent's true reliability profile.

Which metric do you need? Use pass@k when any working solution is acceptable (internal tools, batch jobs, research). Use pass^k when every single interaction must succeed (customer service, payment flows, regulated processes). The gap between the two numbers is where you'll find your production surprises.

Economics

The Hidden Invoice

Most agent cost projections forget four line items that compound with every user.

Biggest line item
Re-Sent Context
System prompts, tool definitions, and conversation state are re-transmitted to the model on every call in a multi-step agent loop. This repeated context — not the actual reasoning tokens — dominates your inference bill.
~62%
of total agent inference cost, on average
Hidden operational cost
The Trust Tax
The ongoing cost of verifying the agent isn't confidently wrong — human QA labor, eval pipeline maintenance, monitoring dashboards. Often the largest hidden expense, and the one that scales linearly with traffic volume.
Ongoing
scales with every new user interaction
ROI timing risk
The 90-Day Illusion
A 90-day ROI window is nearly meaningless. The first three months are dominated by integration costs and debugging cycles. Meaningful agent ROI typically requires a 6–12 month measurement window before the curve turns.
6–12 mo
before ROI becomes legible
Wasted iteration
The Vague Spec Tax
"It should be smart" as your acceptance criteria costs 3× more than specific, measurable ones. A $500 eval pipeline built upfront saves $5,000+ in wasted iteration — teams that skip it spend that budget rediscovering the same failure modes repeatedly.
3×
cost multiplier for vague acceptance criteria

Time saved ≠ financial benefit. If the hours your agent frees up are absorbed into slack capacity rather than redeployed to revenue-generating work, the financial ROI is zero. Measure what that time is used for, not just what was saved.

Process

The Eval Lifecycle

Evaluation isn't a pre-launch checklist. It's a continuous discipline across five stages. (Oracle OCI framework)

1
Qualify
Define capabilities via evals before building. A capability eval is a bet on what the model should be able to do.
2
Test
Run prompts, RAG, tools, and trajectory evals in isolation. Start with 20–50 real failures — not invented scenarios.
3
Gate
Promote passing runs to managed release gates. Regression evals stay near 100%. Capability evals start low and grow.
4
Monitor
Production replay, canary assurance, drop-off rate tracking. Catches what automated evals miss every time.
5
Recover
Turn every incident into a new eval case. Recertify after significant failures. The suite is a living artifact, not a checklist.

Eval saturation warning: When a capability eval hits 100% pass rate, it stops giving you signal. Graduate it to regression (where 100% is the goal) and write harder capability evals. If your entire suite is green, you're not measuring the right things yet.

Glossary — Going Deeper

Words That Need Unpacking

These terms appear in the three external sources and are worth knowing.

Anthropic
pass@k
Probability the agent succeeds in at least one of k attempts. Formula: 1 − (1−p)^k. Use when any working answer is acceptable — batch jobs, internal tools, retry-able tasks. An 80%-accurate agent has a 99.7% pass@5.
contrast with → pass^k
Anthropic
pass^k
Probability the agent succeeds in all k attempts. Formula: p^k. Use when every single interaction must succeed — customer-facing, mission-critical. That same 80% agent has only 32.8% pass^5. This gap is where production surprises live.
contrast with → pass@k
Anthropic
Eval saturation
When a capability eval reaches 100% pass rate, it stops giving you signal — the agent has outgrown the test. The fix: graduate it to your regression suite (where 100% is the maintenance goal) and write harder capability evals. A fully-green suite means you're not measuring the right things yet.
Anthropic
Inter-annotator agreement
Whether two independent domain experts reach the same verdict on an eval task. If they disagree, the task spec is ambiguous — fix the task, not the grader. Used to validate that your eval set is measuring something real and consistent before you trust its scores.
Anthropic
Capability eval vs Regression eval
Capability evals ask "what can this agent do?" — they start at low pass rates and climb as the model improves. Regression evals ask "does it still handle what it used to?" — they stay near 100%. Treating a capability eval as a regression target is a common mistake that masks real progress.
Anthropic
Bypass resistance
Designing evals so the agent can't "cheat" — finding unintended loopholes that pass your grader without actually solving the problem. Common with code-based graders: an agent can satisfy a unit test without writing the right code. Design defensively; review passing transcripts regularly.
Anthropic
Evaluation harness
The infrastructure that runs evals end-to-end: feeding the agent its instructions and tools, executing trials concurrently, and aggregating results. Distinct from the agent harness (the scaffold that lets the model act). Both are being evaluated together when you run evals.
Anthropic
Transcript / Trace
The complete record of one agent trial: every tool call made, the reasoning steps, any intermediate outputs, and the final answer. Reading many transcripts manually is one of the highest-signal activities in agent development — it builds intuition that no automated metric can replace.
Anthropic
τ-Bench / τ2-Bench
Benchmarks specifically for conversational / tool-using agents across multi-turn interactions (τ = "tau"). Unlike single-shot benchmarks, they test whether an agent can sustain correct behavior over an entire conversation. The "2" version adds harder compositional reasoning tasks. Relevant for support, Q&A, and chat agents.
Oracle OCI
Recovery path evaluation
Explicitly testing what happens when something goes wrong mid-task — wrong database, bad input, tool timeout, partial failure. Does the agent recover gracefully or fail silently? This is a behavioral metric that happy-path evals will never surface. Oracle's framework treats it as a first-class lifecycle stage.
Oracle OCI
Release gate
A formal approval checkpoint before an agent version ships to production. Passing runs in your eval suite are "promoted" to the gate, which must clear before deployment. Borrowed from traditional software release management. Adds discipline to agentic deployments that otherwise ship informally.
Oracle OCI
Canary assurance
Running a new agent version on a small slice of real traffic before full rollout — confirming it behaves within the approved envelope on production data before you commit. The "canary" terminology comes from the mining practice of using canary birds to detect toxic gas before it reached miners.
Oracle OCI
State change evaluation
Verifying not just what the agent said but what it changed — files written, database rows updated, APIs called, UI elements modified. Critical for computer-use agents and any agent with write permissions. The environment state after the trial is often more important than the agent's final message.
ODSC
Re-sent context
In a multi-step agent loop, the system prompt, tool definitions, and conversation history are re-transmitted to the model on every single call — even though most of it hasn't changed. This repeated overhead reportedly accounts for ~62% of total agent inference cost. Prompt caching (available via Anthropic and others) directly attacks this line item.
ODSC
Trust tax
The ongoing cost of verifying the agent isn't confidently wrong — human QA labor, eval pipeline maintenance, monitoring dashboards, incident response. Unlike compute costs (which appear on a bill), the trust tax is invisible until someone tracks it explicitly. It scales with traffic and never goes to zero.
ODSC
ROI timeline realism
Most 90-day agent ROI projections are misleading because the first three months are dominated by integration costs and debugging. Meaningful ROI requires a 6–12 month window. Also: time saved only converts to financial benefit if redeployed to revenue-generating work — if it becomes slack capacity, the financial ROI is zero.
Oracle OCI
Groundedness
Does the agent's answer stay within the content it actually retrieved — or does it hallucinate beyond it? A grounded answer only asserts things that are supported by the retrieved documents. The single most important RAG eval metric for research agents, where hallucination outside retrieved content is the primary failure mode.
Oracle OCI
Answer Relevance
Does the answer actually address what was asked? An answer can be factually correct and well-grounded but completely miss the user's question. Measures alignment between the question and the response, independent of whether the answer is correct. Complements Groundedness.
Oracle OCI
Context Relevance
Was the content retrieved actually relevant to the question asked? An agent can generate a grounded, relevant answer and still fail here — because it retrieved the wrong documents in the first place. This is a trajectory metric applied to RAG: did the retrieval step do its job?
Anthropic
RULER (OpenPipe)
Relative Universal LLM Elicited Rewards — an open-source rubric prompt from OpenPipe used to evaluate agent trajectories via LLM-as-judge. Asks questions like "did it achieve the goal?" and "did it avoid unproductive detours?" across multiple trajectory runs of the same task. A starting point, not a final answer — requires customization for your specific agent.
