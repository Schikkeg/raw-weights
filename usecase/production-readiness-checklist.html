01 Core Thesis

Building an AI demo is like building a treehouse — fast, exciting, works great when it's just you.

Taking it to production is building a residential home. Plumbing. Foundation. Safety codes. A roof that holds when it rains.

Most teams learn that the hard way. This checklist is the blueprint for the residential home.

"Everything around the prompt is plain old distributed systems."

— Arpit Chaudhary, technical advisor for Eikos Health

My field notes

"Building an AI demo is exciting. Building a production AI system is unglamorous infrastructure work — and that's the part nobody talks about."

The treehouse-to-residential-home analogy stuck with me because I've built both. The demo works every time I demo it. Then I put real users on it and find out that 90% reliability — which feels great on a laptop — means one in ten interactions fails, and that's before you account for edge cases, rate limits, and the downstream systems that assume the AI always responds correctly. This checklist is my attempt to name everything that lives between "it works on my machine" and "it works in production."

🔩
Your LLM is one node

An LLM call is an unreliable service call — the same way a database can return garbage or an API can time out. You already know how to handle those. Apply the same patterns here.

♻️
You already know the patterns

Retry logic, schema validation, rate limiting, circuit breakers, structured logging — these are distributed systems primitives, not AI inventions. They transfer directly.

🗺️
Four pillars organise it all

Reliability · Cost Effectiveness · Speed · Context Awareness. Every production decision maps to at least one of these four. Navigate by pillar, not by gut.

02 Production Readiness Checklist

Click each item to check it off. Each item includes what Eikos Health actually did — use it as your reference implementation.

Your readiness score 0 / 18

Click items across all four pillars to see where you stand.

  • ✓

    Break your monolith prompt into sequential steps

    Extract intent → validate parameters → confirm with user → execute. Each step is independently testable. A failure in step 2 doesn't re-run step 1.

    Eikos Health: 4-step LangChain pipeline per appointment action
  • ✓

    Add a JSON schema contract between each step

    Define exactly what each step must output. Malformed LLM output triggers a retry at that step only — not at the whole request level. Schema validation is deterministic; LLMs are not.

    Eikos Health: typed output schema on every LangChain step
  • ✓

    Gate irreversible actions behind user confirmation

    The LLM proposes; the user (or a deterministic rule) authorises. Never let the model execute a delete, send, or transfer autonomously. LLMs suggest — code and humans act.

    Eikos Health: cancellation and reschedule surface a confirmation step before writing to DB
  • ✓

    Configure retry count per step, not per request

    Global retry means re-running expensive upstream steps. Per-step retries are cheaper, faster, and preserve partial progress. Retry where it failed, not from the top.

    Eikos Health: step-level retry limits in LangChain
  • ✓

    Run automated quality evaluation on a sample of live responses

    Route ~2% of production conversations through a judge LLM that scores for helpfulness, accuracy, and policy compliance. Human review can't scale — automated scoring at volume is table stakes.

    Eikos Health: LangSmith evaluation with judge model scoring per sampled conversation
  • ✓

    Route cheap models to simple steps

    Intent classification, output formatting, and parameter extraction don't need your most capable model. Reserve expensive reasoning for steps that genuinely need it. Mixing models per step is the unlock.

    Eikos Health: AWS Bedrock multi-model — smaller model for classification, larger for reasoning steps
  • ✓

    Rate limit on token spend, not just request count

    A user who sends 3 requests with 10,000-token prompts costs far more than 30 normal requests. Request-count limits don't protect you. Token quota per user per day — tracked in your application code — is the right lever.

    Eikos Health: token quota enforced inside Lambda; API Gateway handles RPS per IP
  • ✓

    Add a regex guardrail before the LLM

    Obvious off-topic requests, injection attempts, and profanity should never reach the LLM. A simple regex filter catches these for effectively zero cost. Fast, deterministic, free.

    Eikos Health: regex layer is the first filter in the Lambda handler
  • ✓

    Add intent classification to catch scope creep

    The "Chipotle chatbot writing Python" problem: no keyword filter catches that. A lightweight classifier runs after regex and before your main prompt — it denies requests outside your defined scope before running the expensive model.

    Eikos Health: dedicated intent classification step — non-appointment requests denied here
  • ✓

    Track TTFT P95, not average latency

    Time to First Token at the 95th percentile shows worst-case experience for 19 in 20 users. Averages hide the tail where users abandon. P95 is your SLA anchor — track it per step, not just end-to-end.

    Eikos Health: TTFT P95 per step tracked via LangSmith
  • ✓

    Stream outputs — or show a working indicator immediately

    Streaming drops perceived latency dramatically. If your channel doesn't support streaming (WhatsApp Business API doesn't), send a typing indicator the moment you receive the message. Users see activity; they wait more tolerantly.

    Eikos Health: WhatsApp typing indicator sent on receipt — streaming not available via WhatsApp API
  • ✓

    Prompt for crisp, channel-appropriate output

    Verbose LLM responses cost more tokens, take longer to generate, and are harder to read on mobile. Explicitly prompt for concise, conversational replies — especially on messaging channels where walls of text fail.

    Eikos Health: system prompt specifies short WhatsApp-friendly responses
  • ✓

    Move post-response work to an async job

    Sending notifications, writing analytics, updating audit logs — none of this belongs in the critical path. Fire an async job after the user's response is sent. They don't wait; the work still happens.

    Eikos Health: separate notification Lambda fires async after user receives response — sends WhatsApp + email to patient, doctor, and admins
  • ✓

    Use a fast KV store for conversation and checkpoint memory

    Active conversation history needs sub-millisecond reads. DynamoDB, Redis, or any fast KV store — not S3, not a relational DB. Speed matters here because it's in every request's critical path.

    Eikos Health: DynamoDB for conversation history and LangChain checkpoint state
  • ✓

    Use a separate knowledge base for reference content

    FAQs, policies, product documentation — these don't change per conversation but need semantic search to retrieve. A knowledge base keeps your conversation context clean and your system prompt lean.

    Eikos Health: AWS Bedrock Knowledge Base for doctor profiles, office hours, cancellation policies
  • ✓

    Keep app data in your application database

    Appointments, users, orders — these belong in your existing app DB with proper indices and relationships. The LLM only gets IDs. Your code resolves them after the LLM responds. Separation of concerns applies here too.

    Eikos Health: MongoDB for appointment records; LLM sees appointment IDs only, never patient names
  • ✓

    Set a TTL on conversation records

    Old conversations cost storage and are a privacy liability. Set a TTL and let the store delete them automatically — handles compliance without a scheduled job, migration, or manual cleanup.

    Eikos Health: DynamoDB TTL configured — conversations auto-deleted after N days
  • ✓

    Never send PII to the LLM

    The LLM does not need a patient's name to cancel their appointment. Pass an ID; your code resolves it after the LLM responds. This limits blast radius if a prompt is ever extracted, and simplifies compliance logging.

    Eikos Health: LLM sees only appointment IDs — Lambda resolves patient identity after LLM returns its action

03 Eikos Health Architecture

WhatsApp + website → API Gateway → Lambda → LLM + 3 stores → async notifications. Entire stack defined in code; recreatable with one command.

WhatsApp + Website

WhatsApp sends a webhook to API Gateway per message. Website makes direct API calls. Both end up at the same Lambda handler.

Cognito + WhatsApp phone #

Website users authenticate via AWS Cognito. WhatsApp users: Meta vouches for the phone number — Eikos Health trusts that. No separate auth flow needed for WhatsApp channel.

API Gateway

RPS rate limit per IP — first line of defence against DoS. Routes authenticated requests to the appropriate Lambda.

AWS Lambda (Node.js + Express)

All business logic lives here. Express used deliberately (not Lambda-native APIs) — keeps the code portable to ECS Fargate if cold starts become a blocker at scale.

LangChain

Breaks the flow into steps, handles per-step retries, validates schemas, and routes different steps to different models. Also provides the LangSmith integration for tracing and evaluation.

Groq API

Chosen for inference speed over AWS-native consolidation. Fast TTFT matters on WhatsApp where users expect near-instant replies. Bedrock used for model-per-step routing on cost-sensitive steps.

DynamoDB

Active conversation history and LangChain checkpoint state. Fast KV reads, no connection overhead. TTL set for automatic privacy-compliant deletion after retention window.

AWS Bedrock KB

Doctor profiles, office hours, FAQs, cancellation policies. Semantic retrieval lets the agent answer open-ended questions without bloating the system prompt with static content.

MongoDB

Appointment records, patient data, doctor schedules. LLM only ever sees IDs — Lambda resolves them post-response. Known trade-off: Lambda cold start + MongoDB connection overhead adds first-request latency.

Notification Lambda

Fires after user receives response (fire-and-forget). Sends WhatsApp + email (AWS SES) to patient, doctor, admins. Also pushes metrics to CloudWatch for dashboards and alerts.

AWS Amplify + Sentry

Amplify serves the web interface. Sentry captures frontend errors and performance. CloudWatch covers the backend; Sentry covers the browser.

AWS CDK (TypeScript)

Every resource defined as code. If a Lambda is deleted or misconfigured, one CDK deploy rebuilds everything. New region = run deploy again. Only databases can't be recreated from code — their data is irreplaceable.

04 Real Trade-offs Eikos Health Made

Every architectural decision is a trade. These are Eikos Health's actual calls — the thing gained and the thing accepted.

MongoDB requires persistent connections. Lambda cold starts must re-establish that connection each time a new instance spins up — adding latency before any business logic runs. The combination is known to be sub-optimal.

Eikos Health kept it because Lambda's near-zero cost at low volume outweighed the latency cost. The system is functional, just "slightly slower than expected." Arpit's take: not a make-or-break situation at their current scale.

✓ near-zero infra cost ↕ first-request cold start latency

AWS Bedrock was already powering the knowledge base. Using it for inference calls too would have simplified billing, IAM policies, and the overall AWS footprint. But Groq's inference speed was significantly faster — and on WhatsApp, TTFT is the user-facing metric that matters most.

They still use Bedrock for multi-model step routing (cheap model for classification steps), but the primary inference path runs through Groq.

✓ inference speed ↕ AWS consolidation

Lambda's native handler API is simpler and slightly leaner. But Eikos Health used Express as their framework inside Lambda — same code that would run on ECS, locally, or on any container. The trade: a slightly larger deployment bundle and a bit more setup.

The upside: if Lambda ever stops being the right compute layer — cold starts at scale, long-running LLM chains, persistent connection requirements — the migration to ECS Fargate is a config change, not a rewrite.

✓ compute portability ↕ Lambda-native simplicity

WhatsApp Business API does not support streaming — you can't push tokens as they arrive the way a web chat widget can. The workaround: send a WhatsApp "typing…" indicator the instant a message arrives, then send the full response when the LLM finishes.

Real latency is unchanged. Perceived latency drops because the user sees immediate activity. It turns out that knowing something is happening matters more to users than how quickly the first word arrives.

✓ reduced perceived latency ↕ true token streaming

A regex filter catches keywords and obvious injection patterns. But it can't catch semantic scope creep — someone asking a medical appointment bot to write code, translate a poem, or answer geography questions. A lightweight intent classifier runs after regex and before the main LLM, rejecting anything outside the defined domain.

The cost: an extra LLM call on every request that passes regex. The saving: the main, expensive model never runs on out-of-scope inputs. Also reduces attack surface — adversarial prompts that defeat the regex layer often fail intent classification.

✓ cost control + reduced attack surface ↕ extra classification call per request

Writing every resource in TypeScript CDK from the start has an upfront cost: learning curve, more initial setup, and a compile step before every deploy. The alternative — click through the AWS console — is faster day one and unrecoverable later.

With CDK: if a Lambda is accidentally deleted, one deploy brings it back. If the entire environment needs to be reproduced in a different region, it's a config change and a deploy. The only data you can't recreate is what's in the databases — which is exactly why you take backups.

✓ full reproducibility + multi-region readiness ↕ upfront CDK learning curve

05 The Deployment Progression

Not a ladder you have to climb — a set of options matched to scale and complexity. Start where you are.

Tier 1
Lambda

Start here. Pay per invocation, scale to zero, near-zero cost at low volume. Caveat: you pay for idle CPU during LLM wait time; cold starts add first-request latency. Fine for most early-stage AI apps.

Tier 2
ECS Fargate

Move here when cold starts become user-facing, when you need persistent connections, or when workloads are too long-running for Lambda's timeout limit. More control, predictable latency.

Tier 3
Kubernetes

When you need fine-grained workload scheduling, multi-tenant isolation, or cloud portability. High operational overhead. Only warranted at genuine scale or specific compliance requirements.

06 Observability Targets

Track these six. If you're not measuring it, you won't know when it breaks — or why users stopped using it.

TTFT P95
Time to First Token — 95th pct.

Your slowest 5% of users. Use P95, not average — the tail is where trust is lost. Track per step, not just end-to-end. Eikos Health: via LangSmith per-step tracing.

E2E Latency
Full conversation turn — P95

From user message received to user response sent. Captures everything: auth, routing, LLM, post-processing. This is the number users actually feel.

Error + Retry Rate
Per step, not per request

A spike in step-2 retries means step 2's schema is too strict or the model is drifting. Invisible if you only track top-level errors.

Token Spend
By user and by step

Shows which users are expensive, which steps are over-engineered, and which inputs cost 10× the baseline. Your cost forecast lives here.

Judge Score
Automated quality evaluation

Sample ~2% of live conversations through a judge LLM. Score for helpfulness, accuracy, policy compliance. Catches quality regressions before users tell you.

Flag + Refusal
User flags and model refusals

Users flagging responses = signal you can't get any other way. High refusal rate = guardrails too aggressive or prompt too ambiguous. Both need action.

07 Security Surfaces

Three places prompt injection can enter your system. Each needs its own defence — not the same one applied three times.

💬
User Messages

Threat

Conversational prompt injection — "ignore previous instructions and…" Arrives as plain text in the user's message.

Defence

Intent classification rejects out-of-scope inputs before the main LLM. User content is isolated from system instructions in the context window — never concatenated without a clear role boundary.

🔧
Tool Responses

Threat

If your agent calls external APIs or MCP servers, a malicious response can inject instructions into the tool result that the LLM then follows.

Defence

Zero-trust on all model output. The LLM proposes (returns an action); your code validates, authorises, and executes. The model never directly triggers a write, send, or delete.

📚
RAG / Knowledge Base

Threat

Poisoned documents in your knowledge base arrive as retrieved context. The LLM may follow instructions embedded in a document it was told to summarise.

Defence

Isolate retrieved content from system instructions in the prompt structure. Treat RAG content as untrusted user input, not as authoritative directives. Validate that chunks don't contain instruction-like patterns before inclusion.

08 Glossary

LLM
Large Language Model

The AI reasoning component — GPT-4, Claude, Gemini, or self-hosted models. In Arpit's framing: just one unreliable node in your distributed system.

TTFT
Time to First Token

How long until the first character of LLM output arrives. The primary latency metric for streaming interfaces; for WhatsApp use E2E latency instead.

P95
95th Percentile

The latency value below which 95% of requests fall. Better than average for SLA tracking — averages hide the worst 5% who are most likely to churn.

RAG
Retrieval-Augmented Generation

Fetch relevant documents from a knowledge base and inject them into the LLM prompt before generation. Reduces hallucination on domain-specific questions without retraining.

PII
Personally Identifiable Information

Names, phone numbers, emails, medical record IDs. Never send these to the LLM. Pass opaque IDs; resolve them in your application code after the LLM responds.

TTL
Time to Live

A database setting that auto-deletes records after N days. DynamoDB TTL handles Eikos Health's conversation retention policy — zero application code, zero scheduled jobs.

IaC
Infrastructure as Code

Define cloud resources (functions, databases, queues, permissions) in code files. The entire environment becomes reproducible, version-controlled, and auditable.

CDK
AWS Cloud Development Kit

AWS's IaC tool — write infrastructure in TypeScript or Python, deploy as CloudFormation. Eikos Health uses it so the entire stack can be recreated with one command.

Lambda
AWS Lambda

Serverless compute — pay only when your code runs. Scales to zero. Known AI-specific downside: you pay for idle CPU while waiting for LLM response; cold starts add first-request latency.

ECS
Elastic Container Service

AWS service for running Docker containers (Fargate = serverless containers). The recommended next step from Lambda when cold starts or connection management become a bottleneck.

RPS
Requests Per Second

API Gateway rate limit metric. Eikos Health limits RPS per IP to prevent any single user or bot from exhausting shared capacity. Separate from token quotas.

MCP
Model Context Protocol

Open standard for exposing tools to AI agents. Trade-off: exposes your tools to any agent (broad reach) but you cede control over invocation context and rate. If you own the agentic layer, you maintain reliability control.
